# Website database and media backup/restore

`scripts/backup_restore.py` creates a PostgreSQL custom-format dump and a gzip
archive of Django's uploaded-media directory. The manifest records both SHA-256
checksums. The command pauses a running Django backend while it dumps the
database and archives the media volume, then waits for the backend to become
healthy again. If the backend was already stopped, it stays stopped. Other
database writers must also be quiesced for the duration of the backup.

The backup contains both database records and files referenced by CVs, projects,
and Markdown. Static files are generated by `collectstatic` and are not backed
up. Analytics uses its own database and storage lifecycle, outside this website
backup command.

## Tools and credentials

Required on the machine running the command:

- Python 3.10 or newer (standard library only).
- Docker Engine and Docker Compose v2, with access to the correct Docker context.
- A protected environment file containing the Compose settings and database
  credentials for the source stack. For production, use the file created from
  `production.env.example`; do not copy production credentials into the
  repository or use them in a local restore.
- A private output directory with space for a database dump and all uploaded
  media. Backups are not encrypted by this command. Keep them on access-controlled
  storage until ticket58 adds encrypted off-server transfer and retention.

The PostgreSQL client tools and Python media archive/extractor run inside the
Compose service images; they do not need to be installed on the host. Source
services must already be running, and image pulls/builds may require network
access. The backup command needs permission to stop and restart the Compose
backend. It reports command failures on stderr and returns a non-zero exit code.

## Create a consistent backup

Run from the repository root and replace paths and project name with those used
by the running stack. The output directory must not already exist; its parent
must be present. Production output should be outside the repository on a
protected disk or mounted backup destination:

```sh
python scripts/backup_restore.py backup \
  --compose-file compose.production.yaml \
  --env-file /protected/path/website-production.env \
  --project-name personal-website-production \
  --output /protected/backups/website-2026-11-01T120000Z
```

For a local stack, pass `--compose-file compose.yaml`, its `backend/.env`, and
the exact Compose project name used when the stack was started. The resulting
directory contains:

```text
database.dump   # pg_dump custom archive
media.tar.gz    # complete DJANGO_MEDIA_ROOT tree
manifest.json   # format version, creation time, and SHA-256 checksums
```

The backend is briefly unavailable during this operation. The script restores
its prior running state on success or failure. A partial directory is removed
if a backup command fails. Keep the database dump and media archive together;
the restore command verifies their checksums before changing an isolated stack.

## Restore into an isolated local stack

Create a fresh local environment file outside the repository from
`compose.env.example`. Use a new Django secret and PostgreSQL password, and set
a distinct local proxy port and matching site origin (for example,
`PROXY_PORT=3058` and `PUBLIC_SITE_ORIGIN=http://localhost:3058`, free and
different from the source site's port). The target DB credentials can differ
from the source because ownership and grants are omitted from the database
archive. Do not use the production environment file for this step.

Restore always uses the repository's loopback-only `compose.yaml`. The project
name must start with `restore-`, be unique, and must not already own containers
or volumes. The script creates the isolated database first, restores database
and media snapshots, then builds and starts the local site. It refuses a
production Compose file for restore so the verification stack cannot publish
production ingress ports.

```sh
python scripts/backup_restore.py restore \
  --env-file /protected/path/website-restore.env \
  --project-name restore-drill-20261101 \
  --backup /protected/backups/website-2026-11-01T120000Z
```

The restored stack stays running for verification. Check service health, a
known database record, and at least one referenced media file. For example:

```sh
docker compose --project-name restore-drill-20261101 \
  --env-file /protected/path/website-restore.env \
  --file compose.yaml ps
docker compose --project-name restore-drill-20261101 \
  --env-file /protected/path/website-restore.env \
  --file compose.yaml exec backend python manage.py migrate --check
docker compose --project-name restore-drill-20261101 \
  --env-file /protected/path/website-restore.env \
  --file compose.yaml exec backend python manage.py shell -c \
  "from uploads.models import UploadedMedia; print([(m.title, m.file.name, m.file.storage.exists(m.file.name)) for m in UploadedMedia.objects.all()])"
curl -fsS http://localhost:3057/api/v1/health/
```

After the drill, delete only the isolated project's containers and volumes:

```sh
docker compose --project-name restore-drill-20261101 \
  --env-file /protected/path/website-restore.env \
  --file compose.yaml down --volumes
```

Use a new `restore-*` name for every drill. The source stack and its volumes are
never selected by the restore command. For a restore failure, the command exits
non-zero and prints the failed Compose command; it leaves the isolated project
available for inspection and cleanup. Do not delete a backup until a restore
has been checked against the content and media records the operator expects.

`tarfile` validation rejects checksummed archives containing absolute paths,
parent-directory traversal, links, or special files before restore. Protect
backup files against disclosure and modification: checksums detect accidental
corruption but do not authenticate or encrypt them. Ticket58 owns encrypted
off-server transfer, expiry, and visible scheduled-job failures.
